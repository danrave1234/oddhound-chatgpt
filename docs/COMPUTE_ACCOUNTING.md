# Browser compute accounting

Browser provisioning now reserves infrastructure money in PostgreSQL before its one Fly create attempt. The former environment-variable comparison did not debit a shared balance and could not protect against competing workers. Model funding and browser compute are separate ledgers.

`packages/db/compute.ts` owns the operator configuration, atomic reservation, conservative settlement and overdue fence. `browser_compute_budget` has no automatically funded/enabled row. `scripts/configure-compute.ts --apply` requires explicit regional hourly pricing, extra infrastructure headroom, cleanup window, allocation and a rate-source URL valid for at most seven days. Reconfiguration retains spent/held totals, refuses an allocation below committed money and refuses price/region changes with outstanding reservations. Environment variables alone do not replenish the balance. The current fixed preset is shared CPU, one CPU, 2048 MiB; reserve the ceiling of its remaining run lifetime plus the cleanup window, then add configured headroom.

The reservation transaction locks the global admission row, run and compute policy. It checks the kill switch, generation, provisioning state, live lease, exact expiry, rate freshness/region, global outstanding allocation and funds. It inserts the compute reservation and `browser_allocations` row together. A run receives one create attempt. A timeout or invalid response cannot authorize a replacement while its allocation is uncertain.

Cleanup failure retains the full compute hold and run capacity. Unknown creation retains both through the allocation expiry plus 60 seconds, even when an early inventory is empty. Only confirmed provider absence settles the reservation. Settlement charges the entire reserved bound once, preserving conservative headroom rather than claiming a measured Fly charge. It continues to work with the kill switch on, expired pricing, disabled provisioning or absent admission attestation. The independent reaper disables new provisioning and saves an event if any reservation exceeds its cleanup deadline. Clearing that condition needs operator review; it never silently enables itself.

## Verification and limits

Two new tests use actual PostgreSQL transactions to race competing reservations, reject stale generations/wrong regions/expired prices, preserve committed balances across configuration, retain uncertain cost through provider failures/the late-create window, fence overdue cleanup and prove idempotent settlement. The provider responses and time advancement in these tests are **synthetic**; no Fly create or model call occurs. The preceding real [controller-exit probe](evidence/fly-lifecycle-latest.json) is separate deployed lifecycle evidence and did not exercise the new compute reservation path. Current full results are 39 focused tests and 12 local/hosted SQL tests; [hosted evidence](evidence/hosted-postgres.json) records the actual managed database/TLS result.

Production has no enabled compute allocation or approved rate record yet. Do not infer a funding grant from a successful SQL test. The internal reservation is **not a hard cap on Fly's bill**: infrastructure outside the run, image/rootfs storage, traffic, in-flight bytes and prolonged provider cleanup failures require separate headroom and reconciliation. The always-on worker/reaper and explicit engineering probes are outside this per-run pool. Fly's [current pricing](https://fly.io/pricing/) and [October 2026 update](https://fly.io/pricing-update/) price resources separately and vary by region; no unverified monthly forecast or synthetic test rate is deployed.

Platform and origin-verification tokens are now included in the worker's known-secret scrub set before text reaches the model. This is an additional component protection, not complete SELF-05 evidence.
